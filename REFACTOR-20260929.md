# Refactor — batch 1 (2026-09-29)

Two real incidents from 2026-09-19/20 motivated this batch, and both are now
covered by regression tests:

* `orbgen` was invoked on an AiiDA-assembled reference tree and **silently
  started a reference DFT** — `SIAB.abacus.utils.DuplicateCheck` compares the
  whole INPUT, and the assembled one came from the AiiDA plugin (`suffix aiida`,
  no `out_wfc_lcao`), so SIAB classified every folder as new work.
* a spillage run produced `U_gga_10au_100Ry_4s3p2d2f1g.orb` whose header said
  `Number of Gorbital--> 0` — the file name promised a g channel the file did not
  have (`vloc_aux` written where SIAB ignores it), and the report only checked
  file extensions.

No git repository existed, so the pre-change tree is in
`.refactor-backup-<timestamp>.tar.gz` and the two deleted modules are in
`_removed-20260929/`.

## Batch 2 — done

**Grid point directory naming unified.** The workflow used `lmax4_rcut10p0` while
the report layer used `lmax4_rcut10` for the same point, which also meant one
spelling appeared in `static.dft_roots` keys and the other in run trees. Both now
call `interfaces.nsw.point_dir_name()`; the legacy spelling is still *read*
(`point_dir_aliases()`), so trees written before today keep resolving.

**`advanced.py` is gone.** Its three unique capabilities were ported into the
live grid search first:

| capability | how it is expressed now |
|---|---|
| `stop_on_first_valid` | new `Bool` input (default `True`); `False` makes the `iterative` strategy run the whole grid and then choose, which was previously impossible |
| explicit candidates | new `List` input `[[l_max, r_cut], ...]` (`_grid.build_explicit_grid`), for filling gaps in an already-scanned grid; mutually exclusive with `l_max_candidates`/`r_cut_candidates` |
| `max_l_max` / `max_r_cut` | honoured at last (`_grid.cap_grid`): `with_default_abacus` always forwarded them, only `advanced.py` read them |

Its per-*system* ΔE comparison was deliberately not ported (everything else uses
per-atom).

**`batch.py` split** (1754 → 1372 lines), verified by an equivalence check on the
WorkChain specs (inputs / outputs / exit codes / outline identical before and
after):

| module | contents |
|---|---|
| `workflows/batch.py` | the two WorkChain classes only (orchestration) |
| `workflows/_grid.py` | `GridEntry`, grid construction, caps, stopping rule |
| `workflows/siab.py` | `run_siab_pipeline` calcfunction, `build_abacus_child_inputs`, `n_atoms_from_stru` |
| `workflows/results.py` | the four output-`Dict` calcfunctions |

A structural test now enforces that the WorkChain module contains no SIAB call
(`generate_all_from_json(`, `read_stru(`, `subprocess`).

## Batch 2b — found by actually running the pipeline

`aiida-orbgen report` was run against the u_14ve provenance (node 410274, grid
point 410517) with the reference tree on disk. Three things came out of it:

1. **`--siab-json` was ignored in practice.** The SIAB config was read from the
   node's `siab_json` blob *before* the explicit path was considered, so a report
   with a config on the command line still aborted with "cannot recover the SIAB
   config" as soon as the AiiDA object store was unreadable. Fixed by trying the
   explicit path first.
2. **`export_primitive_orbitals` had nowhere to fall back to.** It knew the
   AiiDA repository and the paths recorded at submission time
   (`/tmp/test_orbgen_output/...`, long gone), so every grid point reported
   "no .orb found". It now also looks in `primitive_jy/` of the reference-DFT
   tree(s), which is where SIAB writes the primitive and what survives.
3. **A multi-hour spillage gave no feedback.** The `orbgen` subprocess was
   captured and only appended to the log *after* it exited, so `tail -f` showed
   nothing for the whole run. Output is now streamed into the log file as it is
   produced (the L-BFGS iterations go to stdout, not through SIAB's logger).

It also demonstrated the batch-1 guard doing its job: the u_14ve tree held
**two generations** of reference data — the 100 Ry data of the Sep-19 AiiDA run
(1440 LCAO functions per cell) and the 150 Ry data of the user's own Sep-20 run
(1808) — and the report refused with

    stale: reference data were computed with a different primitive basis
    (1808 LCAO functions per cell, this config expects 1440)

instead of silently fitting orbitals against the wrong wavefunctions. Running it
with a matching (`ecutjy: 150`) config made the guard align INPUT/STRU back to
the 150 Ry primitive and start the spillage.

## Batch 3 — done

**Test suite green.** The 15 failures in `tests/test_project_pbe.py` were a
missing-fixture problem: the module hard-coded `project/pbe`, which no longer
exists (the same data lives in `project/orbgen_api/static`). The fixture
directory is now resolved from a candidate list — original location first — and
the module skips with a readable reason when none is present. 144 passed, 0
failed (87 passed / 15 failed before batch 1).

**One implementation of the ΔE / tolerance / 304 logic** — `workflows/energies.py`
(`is_soft_success`, `pair_energies`, `tolerance_verdict`, `evaluate_energies`,
`best_of`). Before, the pairing arithmetic existed twice, `best` selection twice
and "exit 304 is a soft success" five times, with two consequences: an unpaired
child scored as `0 meV` (looks converged) in one copy and `inf` (rejected) in the
other, and the two grid strategies built their `best` dicts separately.

**A typed, validated view of a run** — `aiida_orbgen/spec.py` (`OrbgenSpec` /
`AbacusSpec`, pydantic). It is now the single place that answers "is this run
describable?", including the checks whose absence cost real time:

| check | why it matters |
|---|---|
| `nzeta[l] <= nbes(r_cut, ecutjy, primitive_type)` | SIAB only notices inside `basistrans`, i.e. after the reference DFT is paid for |
| `len(nzeta) - 1 <= geoms[0].lmaxmax` | same failure mode |
| orbital keys closed per init model | `vloc_aux`/`lloc_min` outside `model_kwargs` are ignored → the g channel comes out empty (the `1g` filename with `Gorbital = 0` header) |
| `checkpoint` points backwards, `geoms` indices exist | caught at submit time instead of inside SIAB |
| `vloc_aux` exists, `ecutjy <= ecutwfc` | either the basis cannot be initialized or the reference is coarser than the basis |
| `out_wfc_lcao: 0` on an LCAO run | the spillage step has no wavefunctions to fit |
| unknown SIAB keys | a typo is otherwise silently dropped |

`utils/config.validate_siab_config` / `validate_abacus_input` keep their
signatures and delegate to it, and **both WorkChains validate every `siab_json`
they are handed** (new exit code 406) — a WorkChain submitted straight through
`WorkflowFactory` no longer reaches SIAB with a broken config.

**The primitive orbital is archived.** `run_siab_pipeline` returned only paths
into the run directory (`/tmp` by default); on 2026-09-19 that directory was gone
and the primitive had to be recovered from the pseudo family. It now also returns
the `.orb` as a `SinglefileData`, exposed as the `primitive_orbital` output,
carried on `GridPoint`, and preferred by `export_primitive_orbitals`.

## Batch 4 — done

**English only.** ~1240 comment/docstring lines across 22 files were translated;
the AST with docstrings stripped is identical for every translated module, and the
only changed string literals are human-facing messages no test asserts on. Two
latent bugs surfaced while reading everything:

* `iterate_step` submitted the next grid point with `self.ctx.grid[idx + 1]`, where
  `idx` never existed (`NameError` on the second point of an iterative search);
* `cli/run.py`'s new `select` path used `json.load(s)` without importing `json`.

Both are now guarded by `tests/test_static_hygiene.py`, which runs pyflakes over
the package (undefined names *and* unused imports) and sweeps src/tests/docs/presets
for Chinese text.

**`extract_energies_step` is ~45 lines.** The node walking moved to
`workflows/extract.py` (`collect_child_energies` → `ChildEnergies`), the ΔE report
lines to `energies.describe_deltas`, and the tolerance block now calls
`energies.evaluate_energies` instead of its own copy of the rule.
`_verify_stru_orbital` moved to `workflows/siab.py` as `verify_stru_orbital` (with
`find_abacus_child` / `expected_orbital_filename`, which no longer hard-codes
uranium). `results.create_energies_dict` lost a second copy of the ΔE arithmetic.

**`aiida-orbgen select` works end to end.** It reads a finished grid search, picks
a point (cheapest acceptable by default, or `--l-max/--r-cut/--calc-pk`), and writes
`selected.json` + `orbgen_<point>.json` + `input.selected.json`. That last one is
*newly runnable*: the point's config goes inline as `static.siab_config`, a key
`ConfigLoader` now understands (it replaces `parameters.orbgen`, is validated like a
preset, and — carrying the point's own `bessel_nao_rcut`/`lmaxmax` — resolves to one
candidate, so the loader picks `orbgen.calc` by itself). Verified against the real
u_14ve provenance: `ConfigLoader(input.selected.json)` → `orbgen.calc`, candidate
`(4, 10.0)`, `ecutjy=150`.

Also: `utils/report/orbitals._apply_grid_point` (a second name for
`interfaces.nsw.apply_grid_point`) is gone, and the package is pyflakes-clean.

## Batch 4b — a pseudo family is content, not just a name (2026-09-29)

Found while preparing a run with a freshly generated `U.pbe-n-nc.UPF` for
`project/u_14ve/` (a 14-valence NC PBE U, md5 `024f9a43…`, versus the
`project/pseudo/U.pbe-n-nc.14ve.UPF` the reference tree was built from, md5
`166049de…`). Both files derive the same family label
`siab-u-nr-pbe-z14-nsw-<rcut>au-150Ry-<lmax>`, because the label encodes element,
xc/rel, zval and the ORB name only. `ensure_pseudo_family` skipped creation whenever
that label existed, so the run would have registered nothing and the LCAO children
would have used the **old** pseudopotential (families pk 218/220) while SIAB's
reference DFT used the new one — a wrong orbital that finishes cleanly.

* `label_for_pair(base_label, upf, orb, existing=…)` — pure, family lookup injected.
  Same ``(UPF, ORB)`` pair → same label (reuse). Different pair → the label plus a
  six-character digest of the pair, and a note naming both sides. The data layer was
  already content-addressed (`AtomicOrbitalData.get_or_create` dedups by md5); only
  the family was not.
* `ensure_pseudo_family` returns the label to use and prints the reason; the
  WorkChain keeps it (`ctx.pseudo_family_label`), hands that to the children, and
  records it as the new optional `pseudo_family` output. An explicit `family_label`
  input used to be honoured by the children but ignored when the family was
  registered — two labels, one run.
* `report` prefers the output over `siab_info.family_label`, so its family fallback
  cannot pick the other pseudopotential's family.
* Also: `static.siab_config_name` (default `inline`) names the run directory for an
  inline config, instead of the awkward `run/static.siab_config/lmax4_rcut10`.

A template for the new pseudopotential lives in `project/u_14ve/` (`input.json` +
`README.md`), with the SIAB config inline so `vloc_aux` — which the shipped preset
still points at the old UPF — cannot silently stay behind. It passes
`aiida-orbgen check` and `run --dry-run`; nothing was submitted.

## Decided against (2026-09-29)

**`OrbgenSpec` as the WorkChain input.** With the inline-config path in batch 4 the
marginal gain is gone: `validate_inputs` already validates the SIAB file with
`OrbgenSpec`, `report` reads the archived config, the file SIAB reads is the
canonicalised dump of a validated preset, and `run` writes exactly what it submits.
Collapsing `siab_json` + `abacus_config` + `l_max` + `r_cut` into one `Dict` would
change the shape of the entry points (and the provenance of every existing node) for
a cosmetic gain, so it stays as it is unless an actual re-derivation bug turns up.
